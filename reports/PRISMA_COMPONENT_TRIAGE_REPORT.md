# PRISMA -- Triage de componentes: útil / ambiguo / innecesario ahora mismo

**Fecha:** 2026-08-01
**Por qué existe este reporte:** tras un inventario completo de todas las "funciones de PRISMA" (sesión del mismo día), el usuario pidió el siguiente paso explícito: verificar cuáles de esos componentes sirven de verdad al propósito de PRISMA y cuáles son ambiguos o innecesarios *en este momento*. Este reporte es solo clasificación/documentación -- no se modificó ningún archivo de producción para escribirlo.

## Resumen ejecutivo

De todo lo inventariado, el **núcleo real** (motor de razonamiento Python+TS, Luz/Snell, ingesta AST y de datos estructurados, storage SQLite, CLI/SDK/visualizer/dashboard reales) está sano, probado, y directamente alineado con la misión y con la dirección de negocio actual. Hay **4 componentes que son fachada o están vacíos** (`ai-bridge`, `formal-lean4`, `benchmarks`, los scripts de "fine-tuning" que no entrenan nada) -- ninguno se está usando ni es dependencia de nada real, así que no rompen nada si se ignoran, pero representan un riesgo de reputación real si alguna vez se muestran como si fueran funcionales. Hay **5 componentes ambiguos** cuya prioridad depende de una decisión de negocio, no de una verificación técnica. Y, de forma incidental durante esta auditoría, aparecieron **2 hallazgos de seguridad reales** en `auth.py`/`server.py` que no encajan en esta clasificación de "utilidad" pero merecen atención pronta.

## B. Ambiguo -- funciona o tiene lógica real, pero la prioridad depende de una decisión de negocio

Estas preguntas son tuyas, no técnicas -- documentadas para que las respondas cuando quieras, no para forzar una acción ahora:

1. **`dual_extraction_validator.py`** -- lógica real (compara extracción de Snell vs. LLM: si concuerdan, `ASSERTED`/`AuthorityLevel.LAW`; si no, `UNDER_REVIEW`/`AuthorityLevel.USER_INPUT`). Esto **encaja directamente** con la idea de negocio que discutimos ("pasar documentos con un LLM grande y verificarlo un par de veces para asegurar sin alucinar"). Hoy está completamente huérfano: cero referencias en `server.py` ni en ningún test. **¿Vale la pena cablearlo ahora como feature real del producto, o se deja en espera hasta que haya un caso de uso concreto?**

3. ~~`storage_postgres.py`~~ -- **RESUELTO (2026-08-01):** mismo criterio que Redis -- prematuro por ahora. SQLite basta mientras no haya un sistema vendible funcionando.

4. ~~`packages/conformance-suite`~~ -- **RESUELTO Y CORREGIDO (2026-08-01):** el usuario pidió eliminar lo falso y arreglar lo real. Se encontró que el problema era más profundo de lo reportado: el paquete **nunca había compilado ni corrido ni una sola vez** -- `package.json` apuntaba a `dist/index.test.js` (un archivo que no existe; el test real se llama `conformance.test.ts`), no tenía script `build`, y no existía ningún `tsconfig.json`. Es decir, el test "real" (Sprint 1 End-to-End) nunca se había ejecutado tampoco, pese a que su código sí era genuino.

   Se corrigió todo: se agregó `tsconfig.json`, se arregló `package.json` (`build`/`test` apuntando al archivo y ruta de salida correctos, se quitó una dependencia fantasma `"@prisma/core": "*"` que causaba un 404 de npm porque nada la resolvía -- el código ya importa `core` por ruta relativa), se **eliminó por completo** el test decorativo ("100 Multi-Domain Conformance Suite", que contaba carpetas de un directorio `examples/` que jamás existió y sumaba `+10/+10` sin aserción real), y se dejó un comentario explicando honestamente por qué se quitó y qué haría falta para una versión real (fixtures reales por dominio, no un conteo de carpetas). Al compilar por primera vez, además, salió a la luz un bug real que estaba oculto (`engine.projectJSON` no existe, es `engine.projectJson`) -- también corregido.

   **Resultado verificado:** `npm test` ahora compila y corre de verdad -- 7/7 tests reales pasando (antes: 0 ejecutados, siempre). `packages/core`'s propia suite (26 tests) sin cambios. Construir una suite de certificación real multi-dominio queda como trabajo futuro, no simulado.

5. ~~**19 endpoints sin test**~~ -- **RESUELTO (2026-08-01):** el usuario pidió que se revisara uno por uno y se decidiera con criterio propio, en vez de preguntar más. Se hizo, y salieron a la luz **dos bugs reales de producción**, no solo huecos de cobertura:

   - **BUG CRÍTICO encontrado y corregido:** `mcp_server` (la integración MCP para que el LLM que el cliente escoja se conecte, decidida en la sesión de arriba) estaba conectado a una instancia del motor **completamente distinta y nunca sincronizada** de la que usan `/api/v1/facts`, `/api/v1/rules`, etc. Existían literalmente dos `PrismaCoreEngine()` separados en `server.py` -- uno de una inicialización temprana y "huérfana" que quedó conectada a `mcp_server`, y otro (el real, persistido, poblado desde SQLite al arrancar) que usan todos los endpoints REST. Cualquier AI conectada vía MCP nunca habría visto ningún Fact/Rule creado por la API normal. Corregido eliminando la instancia duplicada; `mcp_server` ahora usa el motor real. Este es probablemente el hallazgo más importante de toda esta sesión de triage -- rompía en silencio la estrategia que se acababa de decidir.
   - **Bug encontrado y corregido:** `/api/v1/objects/{object_id}` llamaba a `engine.project_json()`, un método que **no existe** en el motor Python -- cada consulta exitosa lanzaba `AttributeError` (solo el camino de "no encontrado" funcionaba). Nunca se detectó porque el endpoint no tenía ningún test. Corregido usando `stringify_canonical()`, la misma utilidad que ya se usa en otras partes del código.
   - **Bug de seguridad encontrado y corregido (no estaba en la lista original, apareció al revisar `/dashboard`):** el panel de administración caía a una contraseña por defecto **hardcodeada en el código fuente** (`"Mejor-futur0"`) si no se configuraba `PRISMA_ADMIN_PASS`. Corregido para negar el acceso por completo si la variable no está configurada, en vez de aceptar un valor conocido.

   **Tests nuevos escritos** (alineados con la misión: motor central, auditabilidad, y la vía MCP que se decidió como la sanción oficial para "el cliente conecta su propio LLM"): `GET /api/v1/objects/{id}`, `GET /api/v1/system/audit`, `POST /v1/mcp/call`, `GET /api/v1/auth/my-key`, y 3 tests para la contraseña del admin dashboard.

   **Deliberadamente SIN test, por decisión de criterio (no por descuido):** `POST /api/v1/natural_language_ingest` y `POST /v1/ingest/text` -- ambos se apoyan en `slm_extractor`/`text_ingester`, ya medidos en 0% de fidelidad real sobre texto real (`PRISMA_REAL_INGESTION_GAP_REPORT.md`) con una métrica `accuracy_rate` que se autoreporta falsamente en 100%. Escribirles tests ahora legitimaría un componente ya documentado como roto, en vez de arreglarlo. Quedan como candidatos concretos para un futuro rediseño (enrutar por Luz, o marcar su salida como `UNDER_REVIEW` igual que se hizo con `is_external_ai_generated`).

   **Baja prioridad, sin acción (triviales o de bajo riesgo):** `/`, `/styles.css`, `/app.js` (archivos estáticos, sin lógica), `/api/v1/system_status` (JSON de estado simple).

   **Mantenido como legítimo pero de prioridad menor (criterio propio, no vestigio a eliminar):** el clúster de "biblioteca de documentos del usuario" (`GET/POST/DELETE/download` bajo `/api/v1/user/library`) y los dos endpoints de feedback (`/api/v1/user/feedback`, `/api/v1/feedback` -- confirmé que NO son duplicados, sirven propósitos distintos). ## C. Innecesario / fachada ahora mismo -- ESTADO FINAL 2026-08-01: implementado según el orden de prioridad acordado (benchmarks -> ai-bridge -> lean4 -> fine-tuning)

- **`packages/benchmarks` -- RESUELTO, ahora real.** El paquete estaba completamente vacío (`package.json` apuntaba a un `dist/runner.js` inexistente). Se construyó `src/runner.ts`: un benchmark honesto que mide DOS números por separado, nunca mezclados en una sola cifra de marketing -- **frío** (inferencia genuinamente nueva cada vez, sin reutilizar caché) y **cacheado** (misma consulta repetida). Resultado real medido en esta máquina: **272 ops/seg frío, 326,109 ops/seg cacheado** (motor TypeScript). Se hizo lo mismo del lado Python (`scratch/prisma_engine_benchmark_honest.py`): **1,333 ops/seg frío, 119,602 ops/seg cacheado**. Esto confirmó y corrigió el hallazgo que motivó todo esto: la descripción de la API en `server.py` decía **"210,000+ QPS"** sin ninguna medición real detrás -- ese número resultó ser exactamente la velocidad de la caché de pruebas (`scratch/ten_million_benchmark_and_evaluation.py` reutilizaba las mismas 6 combinaciones de fact/rule 10 millones de veces, sin generar nunca una inferencia nueva). Corregida la descripción en `server.py` con ambos números reales, medidos y fechados. **Hallazgo aparte, no resuelto (documentado, no arreglado):** `engine.py`/`engine.ts` hacen una copia completa O(n) del espacio de conocimiento en cada inserción (`_update_snapshot`), lo que vuelve la inserción masiva O(n²) -- un primer intento con 50,000 iteraciones no terminó en más de 3 minutos y hubo que matarlo. Es una característica real de escalabilidad a tener en cuenta a futuro, no algo que se arregló en esta sesión.
- **`packages/ai-bridge` -- RESUELTO, reconstruido con un diseño más seguro que el original propuesto.** Al implementar, se encontró que `PrismaCompiler` (el "compilador DSL" que la idea original dependía de usar) tiene un bug propio: su parser de `RULE` **ignora por completo el contenido de la línea** y siempre devuelve la misma regla hardcodeada (edad >= 18), sin importar qué regla se le pida -- nunca detectado porque ningún test ejercitaba un `RULE` con contenido variable. Además, la sintaxis `QUERY` que el `ai-bridge` original usaba como ejemplo de salida **no existe en ningún lugar del compilador real**. En vez de construir sobre ese cimiento roto, se rediseñó el alcance: el LLM (aportado por el cliente, con su propia API key -- nunca uno que PRISMA hospede) solo identifica **qué sujeto/predicado** pregunta el usuario en lenguaje natural; la respuesta real siempre sale de una búsqueda determinística contra el conocimiento YA verificado en el motor (nunca inventada, nunca generada por el LLM). Si no hay ninguna coincidencia verificada, se responde honestamente que no se encontró nada -- nunca se fabrica una respuesta. Implementado con llamadas HTTP reales (OpenAI, Groq, Anthropic, Gemini, con API key inyectable) y una opción sin LLM (`LOCAL_KEYWORD_MATCH`, coincidencia de palabras clave local, honestamente nombrada -- ya no se llama "motor ONNX embebido" como antes, que era pura ficción). **Efecto secundario positivo:** al conectar `ai-bridge` con `packages/sdk`, se encontró y corrigió un bug real de identidad en `sdk.addFact()` -- calculaba el hash SHA-256 sin el campo `kind`, lo que significaba que un Fact creado vía SDK tenía un ID **distinto** al mismo Fact creado vía la API REST, rompiendo la garantía central del Principio 1 ("Truth Has Identity"). También se descubrió que ni `packages/sdk` ni `packages/ai-bridge` ni `packages/conformance-suite` tenían nunca `tsconfig.json` ni un script de test que realmente compilara -- los tres se dejaron funcionando de verdad por primera vez esta sesión.
- **`packages/formal-lean4` -- NO reconstruido; honestamente re-etiquetado.** Decisión explícita: intentar una prueba formal real del SHA-256/RFC8785 de producción en una sola sesión habría requerido experiencia especializada en verificación formal (semanas de trabajo dedicado, como ya se advirtió), y forzarlo rápido habría recreado el mismo problema que se está arreglando. En su lugar, se agregó una nota honesta en ambos archivos: `Theorem1.lean` deja explícito que `CanonicalJSONHash` es una función de relleno (identidad), no el hash real -- el teorema es válido pero no verifica nada sobre el código de producción. `Theorem2.lean` es más defendible (modela genuinamente la propiedad estructural de "no huérfanos"), pero se documentó que nunca se cruzó contra el validador real (`CoreValidator.validate_lineage`). Queda como trabajo futuro explícito, no como progreso fingido.
- **`packages/ai-bridge/scripts/`** (fine-tuning) -- **diferido, tal como se planteó**: solo tendría sentido si el `ai-bridge` real (ya construido arriba) resultara depender de una API de pago poco confiable o cara -- algo que no se sabrá hasta que el `ai-bridge` real esté en uso. No se tocó.

**Guardia de regresión final de esta ronda:** `pytest tests/ -q` -> 98 passed. TypeScript, todos los paquetes compilando y corriendo por primera vez de forma real: `packages/core` 26, `packages/conformance-suite` 7, `packages/sdk` 4, `packages/ai-bridge` 8. Total 45 tests TS reales + 98 Python = 143 tests pasando.

## D. Aparte -- hallazgos de seguridad reales (no forman parte de la clasificación de utilidad, pero aparecieron durante la auditoría) -- **AMBOS CORREGIDOS Y VERIFICADOS el 2026-08-01**

1. **`auth.py` (bypass de autenticación) -- CORREGIDO.** Cualquier string con el prefijo correcto (`prisma_sk_`/`prisma_key_`) que no estuviera registrada se aceptaba igual como válida, con rol "admin" si el string simplemente contenía la subcadena "enterprise" o "live" (atacante-controlada). Se eliminó el fallback; ahora cualquier clave no encontrada en `api_keys` ni en `users` se rechaza con 401, sin importar el prefijo. Verificado directamente (no solo con la suite de regresión, que no cubría este caso): un intento de bypass con `prisma_key_live_enterprise_...` inventado ahora es rechazado; una clave real generada por `create_key()` se sigue aceptando normalmente.
2. **`server.py` (hash de contraseñas sin salt) -- CORREGIDO.** `register`/`login`/`my-key` usaban SHA-256 plano sin salt (vulnerable a tablas arcoíris precalculadas contra todos los usuarios a la vez). Reemplazado por PBKDF2-HMAC-SHA256 con salt aleatorio de 16 bytes y 260,000 iteraciones, en un formato autodescriptivo (`pbkdf2_sha256$<iteraciones>$<salt>$<hash>`) guardado en la misma columna `password_hash` -- sin migración de esquema. Se mantiene verificación de hashes legados (SHA-256 sin salt) solo para lectura, así ningún usuario ya registrado queda bloqueado -- pero cualquier login/registro nuevo produce el formato salteado. Verificado directamente: contraseña correcta valida, incorrecta falla, y un hash legado simulado sigue verificando sin bloquear al usuario.

**Guardia de regresión tras ambos arreglos:** `pytest tests/ -q` → 93 passed (sin cambio, como se esperaba -- ninguna de las dos vulnerabilidades tenía test propio antes, así que la regresión no las cubría; la verificación real se hizo aparte, ver arriba).

## Addendum (2026-08-01): dirección de producto decidida para ingesta por LLM externo -- IMPLEMENTADO

Discusión posterior a este reporte definió la dirección real: Luz sigue siendo el único medio de verificación que PRISMA implementa; nunca se construirá/hospedará un LLM propio para decidir contenido. Para el demo/piloto, si un cliente quiere conectar su propio LLM (a su elección, su costo), lo hace vía la API REST normal (`/api/v1/facts`, `/api/v1/rules`, ya probadas) o vía `mcp_server.py` (`PrismaMCPServer`, confirmado real -- expone solo consulta/inferencia/auditoría sobre conocimiento ya verificado, nunca deja que una entrada externa se vuelva Fact confiable directamente).

Se encontró que `prisma_core/adapters/` (bridges para LangChain/LlamaIndex/CrewAI/`LLMPrismaBridge` genérico) ya existía, con exactamente este propósito -- pero marcaba **todo** contenido de un LLM externo como `LifecycleState.ASSERTED` (mismo nivel de confianza que Luz), sin distinción alguna. Decisión: no usar ese paquete tal cual para el piloto (además, el adapter de LangChain nunca se probó dentro de un pipeline real de LangChain, solo con llamadas manuales a sus métodos).

**Arreglo aplicado en su lugar, en el punto que sí se va a usar (la API REST):** se agregó el campo `is_external_ai_generated: bool` (default `False`) a `FactCreateRequest`/`RuleCreateRequest` en `server.py`. Cuando el llamador lo marca en `True`, el servidor -- no el llamador -- fuerza `integrityState=UNDER_REVIEW` y `authorityLevel=USER_INPUT`, sin importar qué más declare la solicitud. El comportamiento por defecto (campo ausente o `False`) no cambia. Verificado directamente vía `TestClient`: una solicitud normal sigue devolviendo `ASSERTED`/`OFFICIAL`; una marcada como generada por IA externa devuelve `UNDER_REVIEW`/`USER_INPUT` para Facts y para Rules por igual. Regresión: `pytest tests/ -q` -> 93 passed.
